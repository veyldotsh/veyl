# Veyl runtime operations

## Automatic website publishing

The GitHub workflow publishes successful pushes to `main` in `veyldotsh/veyl` to the existing Vercel project serving `https://veyl.sh`. Publishing waits for the contract, application and build checks. Pull requests cannot run the production job. The `production` environment permits only `main`, and a newer main commit causes an older queued release to skip publishing.

`VEYL_VERCEL_TOKEN` is an encrypted GitHub environment secret restricted to the Veyl Vercel project. The current token expires on 31 December 2026; rotate it before expiry. The workflow uses standard GitHub runners, with no additional Vercel team seat. Existing Vercel usage charges still apply. Vercel builds the source remotely, so the workflow does not download the worker gateway secret. Publishing the website does not deploy contracts, enable spending, or upgrade the persistent worker.

## Hosted runtime

Operator examples use `VEYL_SERVICE_USER=veyl` and `VEYL_HOME=/home/veyl/veyl`. Existing hosts can explicitly set both variables to preserve their reviewed account and installation directory without migration. The absolute installation path must end in `/veyl` and contain only the safe path components accepted by `deployment/paths.sh`. Pass both variables through `sudo env` when overriding the defaults.

Vercel serves the static site and a signed HTTP gateway. The persistent Node worker owns encrypted account data, the queue, agent tools and dedicated zkAPI profiles. Each project keeps its own daemon wallet and recovery journal. The shared-host pilot permits **50 registered profiles, at most 10 per owner, with one active daemon pair** on demand. An idle pair can stop only after there are no inference or funding leases and the daemon reports no pending settlement, withdrawal or public return. Profile and wallet files remain in place. An exited parent does not release capacity until its owned process group exits and both ports are free. This is bounded capacity on one machine, not automatic horizontal scaling.

The default durable queue admits 100 jobs, at most 10 per wallet, with one running job globally. Waiting jobs do not retain daemon leases. Reservations are persisted before admission. Restart preserves only queued records that match both ledgers; interrupted dispatch is uncertain and never automatically retried. A queued cancellation keeps its conservative reservation until independently reconciled. Model tool calls can read allowed sources, read Ethereum balances, save project notes and prepare social drafts. They cannot publish, sign transactions or execute arbitrary code.

The installed `deployment/veyl.service` restricts the whole worker and its daemon children to 2 CPU cores, 4 GiB memory (3 GiB soft pressure), no swap, 128 tasks and 384 MiB Node heap. This allocation was raised with owner approval on 2026-10-02 after observing 8 host CPUs, 15.2 GiB total RAM, 9.3 GiB available RAM and 51-66% CPU idle in a short sample. These observations are not a sustained capacity benchmark. Only eight tenant ledgers stay loaded at once; busy ledgers remain pinned and other admissions wait. Each canonical tenant ledger has a 16 MiB bound and reserves output space before paid work. `VEYL_MAX_DATA_BYTES=2147483648` and `VEYL_MIN_FREE_BYTES=536870912` stop new jobs/profiles when Veyl state reaches 2 GiB or free storage falls below 512 MiB. This admission check is cached for ten seconds; it is not a filesystem quota. Recovery files and financial history are never deleted to reclaim capacity.

The worker is installed and active, with its resource limits checked through systemd. As of 2 October 2026, the Vercel website and authenticated gateway are connected, the main market and shared agent factory are deployed and verified on Ethereum, and wallet-approved mainnet transactions, manual zkAPI funding approvals and owner-approved social publishing are enabled. Automatic fee, conversion and treasury operators remain disabled. Real paid zkAPI and social-provider acceptance remain unperformed. `journald@veyl.conf` is installed as `/etc/systemd/journald@veyl.conf` alongside the service's `LogNamespace=veyl` to cap only Veyl logs at 32 MiB with seven-day retention; inspect them with `journalctl --namespace=veyl -u veyl`. Upstream daemon stdout/stderr are discarded because they can contain sensitive operational material. The application exposes sanitized health and project errors instead.

On 2026-10-01, the source-pinned unfunded native daemon passed read-only mainnet metadata and catalog checks: 389 models, 12.645 seconds elapsed, 0.550 CPU seconds and 58.3 MiB aggregate proportional set size across the Node probe, Go client and Rust wallet companion. Evidence: `output/daemon-footprint-20261001.json`. The transient group used **50% CPU, 512 MiB MemoryHigh, 768 MiB MemoryMax, MemorySwapMax=0, TasksMax=64, RuntimeMaxSec=120**. It performed no inference, funding, signing or broadcast. Paid proof peak memory and sustained job throughput remain unmeasured. A hypothetical two-minute job would allow at most 30 jobs/hour in one slot before overhead; that is arithmetic, not a measured service target. Registered profiles are saved wallets, not concurrent agents. Increase slots on a dedicated server only after funded acceptance measurements.

For a hard disk boundary, `create-data-volume.sh` creates a new, fully allocated 2 GiB ext4 image inside `$VEYL_HOME`, refuses existing or nonempty targets, and mounts it at `$VEYL_HOME/worker-data`. The service requires that mount, checks it before startup and writes production state under `$VEYL_HOME/worker-data/production`. The script does not change fstab or another application's files. Never run the worker on an unmounted fallback directory. The worker fails closed on persistence errors. Backups belong outside this bounded data volume.

After reviewing a release and copying its source plus compiled `contracts/out` artifacts to `$VEYL_HOME/releases/RELEASE`, `sudo env VEYL_HOME="$VEYL_HOME" VEYL_SERVICE_USER="$VEYL_SERVICE_USER" bash "$VEYL_HOME/releases/RELEASE/deployment/install-worker.sh" "$VEYL_HOME/releases/RELEASE"` performs the isolated installation. It refuses existing mismatched Veyl units, environment files, current-release pointers or occupied port4320. It verifies the pinned native source, exact control patch, Go build metadata and official wallet/proof bytes before recording binary hashes. This records the inspected existing build; it does not retroactively prove every compiler input. Dependency setup uses the lockfile with lifecycle scripts disabled and a bounded temporary systemd group. Required compiled artifacts must already be present; the installer performs no blockchain build or deployment.

The installer generates three independent keys directly into an owner-only environment file without printing them. It installs only Veyl's data mount, journal namespace and worker service, runs the full unfunded production-module smoke in a temporary restricted group, and starts the loopback worker only after acceptance passes. The smoke checks native catalog/funding metadata and the private HTTP boundary, preserving its separate unfunded wallet files. Repeating the same healthy installation performs no restart. Configuration mismatches require an explicit reviewed migration. The installer does not edit nginx, DNS, firewall rules, fstab, other service files or existing smoke data; new installations default mainnet, daemon-approval and social write flags to false. The current hosted installation was separately authorized to enable those three flags; upgrades preserve that private configuration.

For a subsequent release, use `sudo bash NEW_RELEASE/deployment/upgrade-worker.sh NEW_RELEASE EXACT_CURRENT_RELEASE`, with both absolute paths inside `$VEYL_HOME/releases/`. The upgrader verifies the current pointer, unchanged private configuration, installed resource controls and bounded data volume before preparing the candidate. It checks compiled artifacts and ABI exports, runs an isolated unfunded smoke, then switches the code pointer and restarts only Veyl. Failed health checks restore the old code pointer. Financial journals, wallet files and runtime state are never rolled back or deleted.

Run `install-zkapi.sh "$VEYL_HOME" /path/to/checkout` to reproduce the source-pinned control daemon. It verifies the published ARM64 bundle checksum, applies only the unfunded-control startup patch, tests the public Go packages and records hashes of both binaries and the proof manifest. No configuration wizard, funding, signing or inference is invoked by installation. `VEYL_ZKAPI_MANIFEST` enables hash verification at worker startup. Config profiles require owner-only plaintext files for upstream daemon compatibility; the registry, project memory, sessions, social tokens and queue are encrypted. A server administrator can access the running worker and daemon secrets. This is hosted custody, not sovereign or end-to-end private agent execution.

Secrets go in an owner-only environment file outside the checkout: independent `VEYL_STATE_KEY`, `VEYL_GATEWAY_KEY`, and `VEYL_BACKUP_KEY` (each 32 random bytes as hex), plus any X developer credentials. The Vercel gateway receives only `PUBLIC_ORIGIN`, `VEYL_RUNTIME_ORIGIN` and `VEYL_GATEWAY_KEY`. Never place daemon tokens or wallet state in Vercel, browser assets or Git. X OAuth uses `https://veyl.sh/oauth/x`; its static callback clears the authorization code from browser history, then completes the exchange through the authenticated session. Telegram tokens are entered in the private project connection form. Social publishing and mainnet transaction execution are disabled by default.

Before every paid production inference call, `NoteExpiryGuard` binds the authenticated daemon's selected note to the pinned Ethereum vault at a fresh canonical finalized block. Unknown, closed and expired notes block new calls. A warning begins seven days before expiry; new calls stop three days before expiry. The guard itself is read-only. A separately enabled automatic runway controller can close an idle, verified active note before expiry and prepare a replacement only within the owner's saved policy and approved treasury limits. Ambiguous payments or approvals require recovery and are never resubmitted automatically. An expired deposit may be claimed by the zkAPI treasury, so retaining funds in the Veyl project treasury and withdrawing a whole active note before expiry remain distinct operations. Funding/recovery routes and inference now share a project operation lock, preventing note withdrawal while a job holds its daemon lease. Funding status includes the latest safe public `noteExpiry` report; polling during a job returns its last report without racing the guard.

The production fee keeper is wired but disabled by the installer (`VEYL_FEE_KEEPER_ENABLED=false`). Enabling it later requires a separately approved mainnet-write flag, an explicitly armed dedicated fee-only operator, and all gas/minimum-revenue ceilings. The operator is distinct from the treasury owner/operator, creator and platform. Its allowed transactions are only verified Veyl fee flushes and distributions to fixed recipients; it cannot fund the daemon. Ticks hold the project operation lock, reserve gas before signing, and recover pending hashes without replay. `GET /api/projects/PROJECT/keeper` exposes only that project's records. A separate constrained treasury signer and runway controller are implemented for treasury-to-daemon payments. They require explicit server activation and owner opt-in, remain disabled in the installed preset, and never borrow the fee operator key. Owners can pause future automatic activity even during a daemon or RPC outage; this cannot cancel an already submitted transaction.

The worker saves a heartbeat every 30 seconds; treat timestamps older than 60 seconds as stale. `scripts/check-worker.mjs` checks local health and confirms that direct unauthenticated API calls are rejected. This is an offchain process heartbeat, not proof of successful inference.

For a consistent backup, stop the Veyl worker gracefully and confirm that its exact daemon children exit. Then run `VEYL_DATA_DIR=... node scripts/backup-runtime.mjs backup /path/to/new-backup.enc` with the state and backup keys in the environment. The command refuses an active worker lock or occupied daemon ports, encrypts all snapshot files including upstream wallet state, and prints only metadata. Keep the original state encryption key and the independent backup key recoverable outside the server; never overwrite an existing backup.

Restore with the same script's `restore` action into a **new empty directory**. Restoration validates authentication and per-file hashes, invalidates old sessions and creates `RESTORE_REQUIRES_RECONCILIATION`. The worker refuses to start from that directory. Before releasing quarantine, an operator must reconcile canonical transaction receipts, spent notes/nullifiers, pending approvals and the daemon's recovery state against Ethereum. An old snapshot is not authority to roll back an onchain payment. Preserve the existing data and restore target until reconciliation succeeds.
