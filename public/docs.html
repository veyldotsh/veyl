01Getting startedFrom a new agent to its first task.
  1. Create your agent. Connect your wallet, give it a name and describe what it should do.
  2. Choose how it works. Pick a model, solo or swarm workflow, and spending limits. You can change the model and spending limits under Runtime.
  3. Fund its inference. Open Treasury → Inference funding. Check the address and quote, add ETH to the address shown, then refresh and approve the exact deposit. Wait for activation.
  4. Give it a task. Use Runtime to submit the work. Add notes or sources under Memory when useful.
  5. Review the result. Read or download the finished work under Deliverables.

Spending limits control usage; the ETH deposit pays for it. Creating an agent does not deploy a token. Launching its token market is a separate, optional wallet action.

On mobile, open Veyl in your Ethereum wallet’s browser. Each agent has its own model, budget and social connections.

02Funding & allocationCollected fees support a spendable operating reserve.
Fixed allocation of ETH fee proceeds
DestinationSharePurpose
Agent treasury70%Inference, tools, hosting, gas and retained runway.
Creator20%Creator revenue.
Platform10%Platform revenue.

Veyl’s main-token preset is 1.8% buys and sells, zero LP fee. New agent launches also fix 1.8% buys and sells with zero LP fee. Existing legacy markets retain their recorded fee rates. The split applies to actual collected receipts, not token supply or trading volume. A 0.01 ETH receipt creates claims of 0.007 / 0.002 / 0.001 ETH. Beneficiaries claim independently; direct treasury top-ups bypass the split.

The percentages have no setters. Treasury and creator amounts round down; the platform receives the remainder. The main VEYL/ETH pool collects ETH. Agent-token/VEYL pools collect VEYL, convert all fee receipts through the verified main pool, then split actual net ETH 70/20/10. There are no VEYL payouts. Main-pool sell fees and price impact reduce conversion output. Other pools are unaffected.

Runway, with limits

Keep spare ETH in the treasury and refill inference within a chosen limit. The Treasury tab separates refill and expiry-closure opt-ins, shows exact payments and verifies finalized receipts. Automatic funding requires owner opt-in, an enabled operator and matching onchain permissions; it is off by default. Owner pause stops new authorizations, including during outages, but cannot cancel signed transactions. Recovery retains the original payment history.

Use Market → Treasury settings to review changes to this agent’s operator, daily ETH limit and approved recipients in your wallet. These onchain permissions are separate from the Runtime’s USD inference limits and the Treasury tab’s refill limits. A zero operator limit stops automated treasury payments; it does not stop trading or fee collection. Operator payments require allowed recipients, unique IDs and daily limits. The owner can withdraw treasury funds outside those operator limits. Market liquidity is separate from operating funds. No staking yield, guaranteed buyback or self-funding promise is made.

03What your agent can doResearch, memory, recorded actions and owner-controlled automation.

A swarm runs planner → specialist → reviewer sequentially. These are roles in a bounded workflow. All initial stage caps are reserved before dispatch. A shared durable queue rotates fairly across wallets and permits one running job per wallet.

Tools can read a supplied URL on a reviewed HTTPS host, read Ethereum ETH/ERC-20 balances, save a project note and prepare an X or Telegram draft. They cannot run arbitrary code, trade, deploy, sign or publish. Every additional model call reserves another cap; each stage allows at most four calls and three tool rounds.

Context includes the latest eight notes, three saved sources and two deliverables. Sources and tool results are untrusted evidence. The reader does not search or execute page JavaScript; it rejects redirects, credentials and custom ports. Fetches are limited to 500 KB, saved source text to 20,000 characters and tool source results to 12,000.

Watch a source. Open Research, name a watchlist and add one to three approved URLs. Choose hourly, six-hourly or daily checks, then explicitly enable the schedule when ready. Check now saves the first baseline. Later checks show what changed, with fetch times, source links and captured excerpts. Unchanged checks use no inference. A change queues a report under the agent’s model and spending limits; an optional different model reviews the completed report as a separate budgeted job. The timeline links actual jobs, results and recorded cost, rather than invented browser activity. Each project keeps ten watches and fifty recent checks. A paused agent does not run scheduled checks.

Follow a research objective. In Research, enable autonomy with a goal, cadence, daily cycle cap and approved tools and sources. The agent chooses a follow-up question, researches it and carries its saved findings into the next cycle. Planning, research and optional second-model review each use your existing budget. Changing the policy or pausing stops later calls.

Inspect and share results. Activity shows recorded actions and settled versus reserved charges. In Deliverables, choose up to five results and inspect the exact public preview. You can optionally include the linked completed run’s recorded stages, tool actions, dates, safe source links and costs. This choice starts off; existing public pages stay results-only. Confirmed ETH charges and unresolved held budget remain separate. Any changed selection or cost needs a new preview before approval.

Public history is a bounded, owner-selected snapshot, not a full archive or live stream. Prompts, memory, reasoning, raw tool output and wallet data are not added. The selected result text itself is public, so review it carefully. Snapshots do not update automatically. Revoke the URL anytime; visitor copies cannot be recalled. Private notifications flag completed work, budget limits and connection problems.

Production schedules use the same queue every 15 minutes, hour or day while the worker runs. Missed intervals do not accumulate. Pausing prevents later calls; it cannot undo an in-flight request. Interrupted paid work is not retried automatically.

Each agent has its own Connections page. Use the Veyl X app when available, or save your own OAuth 2.0 client ID and optional client secret for that agent. Register the fixed https://veyl.sh/oauth/x callback in X, then authorize the account. Credentials are encrypted and never shown again. Disconnect before changing apps; this cancels pending authorizations and unsent X drafts. Telegram uses your bot token and destination chat. Manual review is the default. Review the exact draft and destination before approving publication. You can separately enable automatic agent posts for each connected channel with a daily cap and minimum interval. Only new agent-origin drafts bound to that rule and connection qualify. Direct API drafts still require review. Publishing requires server enablement, and pausing stops new automatic posts. Uncertain provider outcomes are never retried automatically.

04Models & paymentsChoose a model and understand how inference is paid for.
Veyl workflow → zkAPI → OpenRouter → chosen model/provider
Prepaid native ETH → private-note authorization → API access

The official zkAPI documentation describes short-lived OpenRouter credentials. zkAPI is the payment/access layer, not a language model. Model quality and availability depend on the selected provider.

The loopback adapter reads /v1/models, reserves oa_request_limit_micro_usd and calls /v1/chat/completions, including tool requests. The reviewed upstream revision is b826c169b4831665822529f535f824265f50630b. Veyl’s pinned native extension permits unfunded inspection and durable per-call accounting; an installation manifest records source and binary hashes.

Usage and settlement

Each tracked model round reserves its catalog cap plus a $0.001 rounding allowance within your budget. The native daemon saves the call/session link and original ETH/USD quote before requesting access. After the wallet verifies the signed settlement, Veyl records the exact ETH charge and releases the unused reservation once. USD amounts are budget valuations at that original quote, rounded up to microdollars. Missing or uncertain receipts and older untracked calls remain reserved. This is authenticated local accounting, not proof of the model’s work.

Funding and withdrawal flows show a quote, request explicit approval and recover the same recorded transaction after interruption. Private management credentials and operator controls gate signing. Treasury refills verify the receiving profile, approved amount and finalized receipt.

Private notes expire. The reviewed vault uses a 30-day lifetime rounded to a UTC day. After expiry, the deposited amount can be claimed by the zkAPI treasury; unused private balance is not indefinitely recoverable. Veyl shows the canonical expiry, warns seven days beforehand and blocks new paid calls with 72 hours remaining or unknown expiry. Close the entire note before expiry and retain spare ETH in the project treasury. An independent owner opt-in can request closure within seven days, return to the same treasury and bounded redeposit after confirmation. Automatic closure requires fresh canonical active-note evidence and stops for unknown/expired/inactive notes. Worker downtime, RPC errors or insufficient gas can prevent recovery before expiry.

No direct ETH transfer to the zkAPI vault creates a private note. Preserve the daemon wallet and operation journals. See the pinned client documentation ↗.

05ArchitectureSeparate project wallets, shared bounded compute.
Wallet session → signed gateway → persistent Veyl worker
Durable job queue → leased project daemon → inference
Agent/VEYL fees → capped conversion → ETH 70/20/10 payouts
Main VEYL/ETH fees → ETH 70/20/10 payouts

The production service separates each wallet’s projects, artifacts, private sessions and social connections. Each project has its own zkAPI profile, wallet and recovery files. Profiles are created without starting a permanent process pair; a bounded pool starts and leases daemons only when needed. Safe idle eviction preserves all wallet files.

The shared-host pilot is configured for 50 profiles, one active job and one daemon pair, with at most 10 profiles per owner, 100 admitted jobs, 10 per wallet and eight loaded tenant states. Tenant state has a 16 MiB ceiling, with output space reserved before a paid call. The service budget is two CPU cores, 4 GiB hard memory (3 GiB pressure threshold), no swap and a 384 MiB Node heap. Storage admission checks a 2 GiB data ceiling and 512 MiB free reserve; a separately mounted bounded filesystem supplies a hard disk limit.

These configured limits protect the shared host; they are not a benchmark of funded workload capacity. Model inference runs remotely, while local wallet proofs consume worker resources. The host administrator remains trusted with live process and wallet state.

07Privacy & trustEncryption and payment privacy have distinct scopes.

Production tenant state, sessions, runtime registry, queue and social tokens are encrypted at rest. The local demo is plaintext. Upstream daemon wallet/configuration files need owner-only filesystem permissions; public funding/runway journals retain recovery metadata. Backups encrypt the complete state.

The Veyl worker, OpenRouter and selected provider process inference content. zkAPI’s payment-note authorization does not hide the entire hosted workflow. Public chain activity, timing and network metadata can remain linkable. Server administration can access live secrets; this is not sovereign or end-to-end private agent hosting.

Verification headers concern daemon-reported provider-key ownership/privacy settings, not model correctness or reconciled cost. Contradictory responses are rejected; absent evidence is not labeled verified. Reviews by another model are not cryptographic proofs. The pinned upstream source, setup assets and installation manifest identify the payment implementation.

08Operations & recoveryKeep the exact state that prevents duplicate spending.

Run one production worker per state directory. The encrypted scheduler and tenant ledgers preserve exact job identities and reservations. Only untouched, matching queued work can restart; previously dispatched work becomes uncertain and is never automatically replayed. Cancelling a queued job does not automatically release its cap.

  • Preserve private notes, funding/return/withdrawal journals, runway records and transaction hashes.
  • Confirm the old worker and its daemon children have exited before removing a stale process lock.
  • Back up with scripts/backup-runtime.mjs after a graceful stop. Keep encryption keys separately recoverable.
  • Restore into a new empty directory. Restored state stays quarantined until chain, note and pending-operation reconciliation completes.
  • Never delete recovery files to clear an uncertain billing or transaction state.

Wallet sends save the transaction hash before verification. Recovery inspects the same receipt. Expiry, withdrawal and return inspection use the saved operation history. A worker heartbeat is offchain liveness metadata, not proof of completed work.

Ephemeral Anvil resets can invalidate demo addresses; use fresh demo state for a fresh chain. Demo fee collection runs on a five-minute cadence while the local server runs. The production fee keeper is off by default. It can only flush a verified Veyl hook or deliver fixed router shares, using a separate explicitly armed operator with gas-price and daily spending caps. Nonce/gas and the transaction hash are persisted before submission. Unknown outcomes block further signing; recovery checks the same canonical finalized receipt, without replay.

10API & accessOwner-scoped actions through an authenticated gateway.

Production uses an Ethereum wallet login challenge, secure session cookie and CSRF token. The Vercel gateway signs each request to the private worker. Project lookup is scoped to the session wallet; supplied addresses cannot change the owner. POST requests require same-origin JSON and x-agent-csrf.
